# WORK HUB フェーズA報告：現状調査と設計提案

作成日: 2026-11-14 / 対象: 株式会社生田プリーツ 社内業務共有アプリ（仮称 WORK HUB）
位置づけ: 開発指示書 v0.1 のフェーズA成果物。**本番環境・外部サービス・本番データへの変更は一切行っていない。**

---

## 1. 結論（先に）

1. **実装方式は「Google Apps Script（GAS）で画面もAPIも配信する社内Webアプリ ＋ 専用スプレッドシートをDBにする」を推奨する。**
   - 社員のGoogleアカウント（iquta.comドメイン）でログインし、サーバー側（GAS）で本人確認と権限判定ができる。認証コードを自作しない。
   - 新しいサーバー・DB・月額費用・秘密情報管理が増えない。既存の運用（スプレッドシート、GAS）の延長で管理できる。
   - 既存の生産管理アプリ（sewing-tracker）、問い合わせアプリ、受付フォームには**一切触らない**。別のApps Scriptプロジェクト、別のスプレッドシートとして独立させる。
2. **既存の実装パターンのうち、以下は踏襲しない。** 理由は後述。
   - JSON全体を1回で上書き保存する `save` 方式（同時利用で他人の更新を消す）
   - クライアント側だけの閲覧コード判定、クライアントに埋め込んだ合言葉トークン
   - GASコードをリポジトリ外（GASエディタ）だけで管理する運用
3. **第1段階（MVP）は「手入力の案件・決定・タスク・メモ・履歴・アプリ内通知」のみ。** AI抽出、Gmail取り込み、生産管理との連携は設計上の受け口だけ用意し、実装しない。
4. **最大のリスクは技術ではなく「使われなくなること」。** 設計の優先順位は「朝イチで自分の仕事が見える」「3タップで完了・登録できる」「入力しなくても叱られない」に置く。

### 2-3. フロント⇄GAS の接続方式（既存）

- 読み込み: `GET <GAS exec URL>` で全データを1回取得。ポーリングなし。タブ復帰時に再読込。
- 書き込み: `POST`、`Content-Type: text/plain`、本文 `{action, ...}`。応答 `{status:"saved"}`。
- 失敗時: localStorage に未送信キューを保持し再送。ID重複排除で二重行を吸収。
- 受付フォームは `mode: "no-cors"` の投げっぱなしで、成功判定ができない。

### 2-5. 未確認事項（回答が必要）

1. **社員全員が iquta.com の Googleアカウントを持っているか。** 持っていない社員がいる場合、アカウント追加（Workspace の有料ライセンス）か、共用アカウント（監査性が落ちる）かの判断が要る。これが設計の前提。
2. ホスティングが GitHub Pages か。WORK HUB は GAS 配信なので直接の影響はないが、既存アプリの変更時に関係する。
3. 利用人数、端末（個人スマホ／共用PC／工場タブレット）、工場内の通信環境。
4. 生産管理GASのコードとシート構造（第3段階の連携時に必要。今回は不要）。
5. 「他部署に見せない案件」が実際にどれくらいあるか。少なければ権限設計を簡素にできる（後述）。

## 3. 実装方式の比較と推奨

| 案 | 構成 | 利点 | 欠点 | 判定 |
|---|---|---|---|---|
| **A（推奨）** | GAS HtmlService で画面配信 + `google.script.run` でサーバー関数呼び出し + 専用スプレッドシート | Googleログイン・サーバー側本人確認が標準機能。追加費用ゼロ。データを担当者がそのまま表計算で見られる。バックアップ＝ブックの複製 | URLが `script.google.com/...` になる。スプレッドシートの同時書き込みは LockService で直列化が必要。数万行を超えると遅くなる | **採用** |
| B | 既存と同じ GitHub Pages 静的ページ + GAS API（誰でも実行）+ Google Identity でIDトークン検証 | 既存アプリと同じ配信方式。PWAの自由度が高い | 認証コードを自作する。Cloud Console でOAuthクライアント設定。トークン失効の扱いが煩雑。実装・運用ミスの余地が大きい | 不採用 |
| C | Vercel + Next.js + Postgres（Supabase等）+ Google OAuth | 権限・検索・履歴がDBで素直に実装できる。長期的な拡張性は最良 | 新しいホスティング・DB・秘密情報管理・デプロイ手順が増える。社内に保守できる人がいない前提では運用負荷が重い | 将来の移行先候補 |

**Aを選ぶ理由（生田プリーツの文脈）**
- 既に GAS + スプレッドシートで生産管理が回っており、社内の「触れる人」の範囲がここ。新技術を増やすより、同じ道具で安全側に寄せる方が続く。
- 社員数十人規模・1日数百件以下の更新であれば、スプレッドシートの性能限界には当面届かない（推測。利用開始後に行数を監視する）。
- 行追加・1行更新・追記ログを徹底すれば、既存の「丸ごと上書き」より安全になる。
- 第2段階のAI連携も、inquiry-engine.gs と同様に GAS から Anthropic API を呼べばよく、構成を変えずに進める余地がある。

**Aの弱点への手当て**
- 同時書き込み: すべての書き込みを `LockService.getScriptLock()` で直列化し、1行単位で追加・更新する。全体上書きは禁止。
- 読み込み速度: 初回は必要なシートだけ読み、完了済みタスクは直近3か月に絞る。CacheService でマスター（users, teams）を数分キャッシュ。
- 行数増加: 年単位でアーカイブブックへ移す運用を最初から手順化する。
- 将来の移行: データ層を `Repo_*` 関数に閉じ込め、画面やロジックがスプレッドシートAPIを直接触らない構造にする。

## 4. データ構造（スプレッドシート「WORKHUB_DB」）

1行＝1レコード、1行目＝ヘッダー。ID はサーバー側で生成（時刻＋乱数、例 `T20261114-9f3a2c`）。削除は `deleted_at` を入れる論理削除。日時は ISO 8601（JST, `+09:00`）で保存し、表示もJST。

| シート | 主な列 | 備考 |
|---|---|---|
| users | id, email, name, team_id, role(admin/leader/member), active, sewing_member_id?, created_at | email がログインの鍵。sewing_member_id は生産管理 `members.id` との将来の対応付け用（空でよい） |
| teams | id, name, sort | 初期値は生産管理の Aチーム／Bチーム／Cチーム／サンプルチーム ＋ 事務・営業など |
| projects | id, title, type(顧客/加工/社内改善/その他), customer_name?, team_id, owner_id, summary, lifecycle(検討中/進行中/保留/完了), visibility(全社/部署/限定), existing_production_id?, created_by, created_at, updated_at, deleted_at | 既存生産管理の品番IDは参照用に文字列で保持。連携はしない |
| project_members | project_id, user_id, access(閲覧/編集) | visibility=限定 のときの許可者。責任者は自動で編集 |
| source_records | id, project_id, kind(会議/商談/メモ/メール), title, occurred_at, raw_text, source_url?, visibility(案件に従う/限定), author_id, created_at, deleted_at | 議事録の原文を置く場所。メール取り込みは第2段階で kind=メール を使う |
| decisions | id, project_id, source_record_id?, title, details, state(検討中/判断待ち/決定済み/見送り), owner_id, decision_maker_id?, decided_at?, created_by, created_at, updated_at, deleted_at | 「決定済み」でもタスクは完了にならない |
| action_items | id, project_id, decision_id?, source_record_id?, kind(作業/確認/判断), title, details, assignee_id, due_date?, state(未着手/進行中/回答待ち/完了), waiting_on?, completed_at?, created_by, created_at, updated_at, deleted_at | 期限超過は保存せず `due_date < today && state != 完了` で算出。「確認依頼」は kind=確認 |
| comments | id, entity_type, entity_id, body, author_id, created_at, deleted_at | 案件・決定・タスクに共通 |
| activity_logs | id, actor_id, entity_type, entity_id, action, field?, before?, after?, at | 追記のみ。更新・削除不可。取り消しもログに残す |
| notifications | id, user_id, type(新規担当/確認依頼/期限接近/期限超過/決定更新), entity_type, entity_id, message, read_at?, created_at | 同一 user×type×entity は未読のうち1件まで（重複防止） |
| settings | key, value | 期限接近の日数（既定3日）、デモモードフラグなど |

**設計上の約束**
- 顧客名は `customer_name` に独立して持ち、入力時に既存値から選択（表記ゆれ防止）。
- `activity_logs` と `notifications` は追記専用。他のシートもサーバー関数経由でしか書かない。
- デモデータは別ブック（`WORKHUB_DB_DEMO`）。画面上部に「デモ環境」帯を常時表示し、本番と視覚的に区別する。

## 5. 権限設計（MVP）

**基本方針: 既定は「全社で見える」。例外として「限定」を使う。** 数十人の工場で案件の大半を隠すと、共有という目的が死ぬ。指示書の「最小権限」は、限定案件と情報源レコードの保護で満たす。

| 操作 | member | leader（部門責任者） | admin |
|---|---|---|---|
| 全社案件の閲覧・コメント | ○ | ○ | ○ |
| 部署案件の閲覧 | 自部署のみ | 自部署のみ | ○ |
| 限定案件の閲覧 | project_members に含まれる場合 | 同左 | ○ |
| 案件の作成 | ○ | ○ | ○ |
| 案件の編集・限定設定 | 責任者または編集権のある関係者 | 自部署の全案件 | ○ |
| 決定・タスクの作成 | 閲覧できる案件に対して○ | ○ | ○ |
| タスクの状態変更 | 自分が担当のもの＋閲覧できる案件のもの（履歴に残る） | ○ | ○ |
| 決定を「決定済み」にする | 決定の owner または案件責任者 | ○ | ○ |
| 情報源（原文）の閲覧 | 案件権限＋レコードの visibility を両方満たす場合 | 同左 | ○ |
| ユーザー・チーム・権限の管理 | × | × | ○ |
| 論理削除 | 自分が作成したもの（24時間以内） | 自部署 | ○ |

- 判定はすべて GAS 側の `can(user, action, entity)` で行い、画面側の非表示は補助に留める。
- ログイン直後に `users` に存在しないアカウントは「未登録」画面を出し、admin が有効化するまで何も見せない。

## 6. 画面構成

試作品（ikuta-workhub-prototype.html）の5タブ構成を踏襲し、日常運用のために以下を調整する。

| 画面 | 内容 | 試作品からの変更点 |
|---|---|---|
| ホーム | 要対応件数（未完了／確認依頼／判断待ち／期限超過）、今日と期限超過の自分の仕事、関係案件の新しい決定、通知 | 「表示」切替（他人の分を見る）はホームから外し、「自分の仕事」画面のフィルターへ移す。常に自分が主役 |
| 自分の仕事 | 期限順一覧、状態フィルター、ワンタップで「進行中→完了」 | 完了は一覧上のボタンで即実行、取り消しリンクを3秒表示 |
| 案件 | カード一覧（区分・状態・担当・件数）、検索、詳細（概要／未決／やること／確定事項／時系列／元資料） | 詳細はドロワーではなく1画面にする（スマホで戻れる） |
| 決定事項 | 全社の決定・未決一覧、状態フィルター、詳細（根拠・決定者・履歴・関連タスク） | 「決定済み」操作時に「関連タスクは完了になりません」を確認表示 |
| 情報登録 | 記録名・案件・原文貼り付け → 保存後、同じ画面で決定／タスク／未決を手で追加 | AI抽出は「AI候補（未確定）」枠を置くが MVP では非表示 |
| 通知 | ベルアイコンからの一覧、既読化 | 新規 |
| 管理（adminのみ） | ユーザー有効化、チーム、設定 | 新規 |

**共通の作り**
- フォントは BIZ UDPゴシック（印刷領域だけでなく全体）。配色は生産管理の青系変数（`--iquta`, `--ink`, `--aka` 等）を流用。
- 状態は色＋文字ラベル。期限超過は赤文字＋「期限超過」の文字。
- 360px幅で下部ナビ5つ。入力欄は大きく、ドロップダウンは標準部品を使う（工場で手袋越しでも押せる）。
- 画面上部に環境表示（本番／デモ）。
- 3操作以内の目安: ホーム→タスク→完了ボタン（2操作）、ホーム→「＋」→内容と案件→登録（3操作）。

## 7. 技術構成（WORK HUB プロジェクト）

```
workhub/                     ← 既存ファイルと分離した新ディレクトリ
  .clasp.json.example        ← scriptId を入れない雛形（実物はコミットしない）
  appsscript.json            ← webapp: executeAs USER_ACCESSING / access DOMAIN
  server/
    Main.gs                  ← doGet（HTML配信）、公開API関数（api_* のみ公開）
    Auth.gs                  ← getCurrentUser(), can()
    Repo.gs                  ← シート読み書きの唯一の窓口（Lock, ID生成, 論理削除）
    Services.gs              ← 案件/決定/タスクのユースケース、履歴・通知の生成
    Notify.gs                ← 期限接近・超過の集計（時間主導トリガーで1日1回）
    Setup.gs                 ← 新規DBブックの作成・ヘッダー生成（本番では実行確認付き）
  client/
    index.html, styles.html, app.html（React UMD + Babel standalone、既存と同じ方式）
  tests/
    *.test.js                ← 純粋関数（権限判定、期限計算、通知重複判定）をNodeで実行
  README.md                  ← 構成、デプロイ手順、バックアップ・復旧、既知の制限
```

- **コードはリポジトリで管理し、`clasp push` で反映する。** 既存の「GASエディタで手作業」運用は WORK HUB では採用しない（Apps Script API の有効化が必要）。
- スクリプトプロパティ: `ENV`（dev/prod）, `DB_SHEET_ID`, `DEADLINE_SOON_DAYS`。値はコミットしない。
- dev と prod は**別の Apps Script プロジェクト・別のブック**。dev から prod ブックIDを設定できないよう、`Setup.gs` で ENV とブック名の一致を検査する。
- バックアップ: 毎日深夜に `DriveApp.makeCopy` でブックを複製し、30日分保持（GASトリガー）。復旧は複製ブックのIDを `DB_SHEET_ID` に差し替えるだけ。手順を README に書く。
- 既存 `tests/` と同じ Node 実行方式に合わせ、ランナーは入れない（必要なら後から）。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 使われなくなる | 最大。全てが無駄になる | 会議ごとに記録係を1人決める。社長が毎朝ホームを見て口頭で参照する。最初は会議だけを対象にし、メールや雑務は入れない |
| Googleアカウント未保有の社員 | ログインできない | 事前に確認（未確認事項1）。全員分のアカウントが前提 |
| スプレッドシート同時書き込み | 更新の消失 | Lock＋1行更新。全体上書き禁止。活動ログで復元可能 |
| GASの実行制限・応答遅延 | 操作が待たされる | 読み込みを絞る、キャッシュ、保存中表示、失敗時の再送キュー（既存の仕組みを踏襲） |
| 権限を厳しくし過ぎる | 共有されない | 既定は全社公開。限定は例外運用 |
| 監視ツール化 | 社員の反発 | 個人別の完了率・遅延数などの集計画面を作らない。履歴は「誰がいつ変えたか」の追跡に限定 |
| 本番と開発の混同 | 本番データ破損 | 別プロジェクト・別ブック、環境表示帯、Setup の整合性検査 |
| 行数増加 | 速度低下 | 年次アーカイブ手順。閾値（例: 1万行）で警告ログ |

## 10. 検証方法

- 単体: 権限判定 `can()`、期限超過算出、通知の重複抑止、ID生成の一意性を Node テストで確認。
- 結合（dev）: 2アカウントで同じタスクを同時更新し、両方の変更が履歴に残ることを確認。
- 権限: member アカウントで限定案件の URL を直接開いて拒否されることを確認（画面の非表示ではなくサーバー応答で）。
- 端末: iPhone/Android の実機で 360px 幅、Chrome と Safari。
- 復旧演習: バックアップ複製から `DB_SHEET_ID` を切り替え、画面が復元されることを確認。
- 既存アプリ非干渉: 既存の HTML・JSX・GAS に差分がないことを `git diff` で確認。

## 付録: 試作品（ikuta-workhub-prototype.html）の確認結果

- 5タブ構成（ホーム／自分の仕事／案件／決定事項／情報登録）、右側ドロワーで詳細表示、localStorage に保存する単体デモ。
- 決定状態（検討中／判断待ち／決定済み／見送り）とタスク状態（未着手／進行中／回答待ち／完了）が分離されており、「決定済みにしてもタスクは完了にならない」注記も実装済み。設計の骨格としてそのまま採用できる。
- 期限超過は算出式（`due < today && state != 完了`）。採用。
- 「整理のデモを見る」は固定サンプルの表示で AI 処理ではないと明示されている。MVP でも同じ姿勢を踏襲する。
- 配色は緑系（`--sea:#296969`）。生産管理アプリとの統一のため青系に変更する。
